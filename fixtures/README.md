# Original hardware compatibility probes

All source (`compat.asm`, `gdma.asm`, `sound.asm`, `sweep.asm`, `startup.asm`, `buslock.asm`, `fpo1-poll.asm`, `multiply.asm`, `conversion.asm`, `divide.asm`, `push-sp.asm`, `rtc.asm`, `shift-rotate.asm`, `internal-eeprom.asm`, `a0.asm`, `raw-rom.asm`, `lcd.asm`, `lcd-output.asm`, `word-timing.asm`, `keypad.asm`, `build.py`), generated cartridges in `generated/`,
and test graphics/sound data in this directory are original work authored for
this repository for Issues #11, #13, #19, #21, #23, #25, #27, #29, #31, #33, #35, #37, #39, #41, #43, #45, #47, #51, #53 and #55, dedicated to the public domain under **CC0-1.0**
([full license](LICENSE)). No downloaded ROM, BIOS, emulator implementation,
game asset, font, or audio recording was used. Graphics are constant tile planes
or packed nibbles; sound is a square wavetable generated by cartridge instructions.
The native bank vectors in `ws-core` tests are also generated directly in memory.

Rebuild with Python 3 and NASM (no third-party libraries):

```sh
python3 fixtures/build.py
python3 fixtures/build.py --check
cargo test --workspace --locked
```

Each image has a reset far jump, typed header and additive checksum. Images are
128 KiB except the raw 3/6 MiB probes below.
The source is assembled for F000:0000 in the last bank. The leading bank contains
an original constant marker. Hardware probes are deliberately small programs,
not compatibility patches or commercial-game substitutes.

`buslock.asm` builds the original CC0 `buslock.ws` (128 KiB, 32 KiB SRAM).
Explicit F0 bytes avoid applying NASM's x86 LOCK-target restrictions to V30MZ.
It runs through the normal footer/final bank on all three models and exercises
memory reads/writes, displacement/immediate operands, read-only CMP and flags,
RMW, implicit stack operations, all byte/word immediate/DX IN/OUT forms, seven
mixed/repeated prefixes, bounded REP, NOP and register arithmetic. It draws green
or Mono gray 170 on pass, red or gray 187 on failure. CPU-produced RAM words
0400–0418 are copied to cartridge SRAM 0000–0018:

| RAM word | Independent expected result |
| --- | --- |
| 0400 | 600D pass (0BAD failure) |
| 0402 / 0404 | ABCE memory RMW / 005A byte load |
| 0406 / 0408 | F046 comparison FLAGS / 1234 stack round trip |
| 040A / 040C | 3210 immediate-port / 7654 DX-port word readback |
| 040E | BEEF after seven mixed prefixes, last segment ES |
| 0410 / 0412 | 1234 / 5678 copied by seven-prefix REP MOVSW |
| 0414 / 0416 | 2468 register arithmetic after NOP / F000 actual CS |
| 0418 | Retained boot count, incremented on restart |

Native integration and the complete production Wasm/player compatibility suite
assert these CPU-written values against independent literals on every model,
including restart with fresh boot counts. Browser file selection and actual SRAM
flushes retain the existing local ROM/save handling. Unit vectors separately
check exact IP, registers, flags, RAM, ports, bus accounting, diagnostic propagation
and IRQ/REP boundaries. These are emulator regressions, not physical bus timing
or commercial-title results. See [BUSLOCK reconciliation](../docs/hardware-subset.md#buslock-source-reconciliation-issue-35).

The four `startup-{mono,color}-{common,2003}.ws` cartridges are original Issue #33
CC0 probes from `startup.asm`: mono-compatible and Color-only headers, each with
common and Bandai 2003 mapping. They establish ES=0 explicitly and capture incoming
SP at RAM 0400 and DS at 0402 before replacing either; they never assume incoming
DS, ES or SS for destination addressing. The normal FFFF:0000 footer jump reaches
F000:0000 in the final bank. Literal CPU checks require SP=2000, DS=FF00 on Mono
or FE00 on Color/Crystal. RAM 0404 records incoming A0 (8D/8F), 0406 records CS
(F000), and 0408 is 600D on success or 0BAD on failure. Headers request both ROM
width/wait flags and protected internal EEPROM; the probe never changes console
records. SRAM words at 0000/0002/0004/0006/0008/000A contain the retained boot
count, captured SP, captured DS, result, A0 and CS. The program deliberately ends
with SP=3456 and DS=1234, then HLT, so later lifecycle checks detect stale state.
Native tests and the production browser compatibility suite check the raw markers
against independent literals for load, restart, replacement and compatible model
changes. The browser uses real player save flushes and the compiled Wasm adapter.
The [startup policy and source limits](../docs/hardware-subset.md#firmware-free-startup-and-reset)
explain the inspected WSHWTest observations that motivate these original probes;
no third-party assembly or firmware bytes were copied.

| Cartridge | Save | Mapper interface | Color rendering |
| --- | --- | --- | --- |
| `sram32-common.ws` | 32 KiB SRAM, including 8000 mirror | Common C0–C3 | 4bpp planar |
| `sram128-2003.ws` | 128 KiB SRAM, independent banks 0/1 | Bandai 2003, GPO, self-flash read mapping, RTC absence | 4bpp planar |
| `eeprom128.ws` | 128-byte EEPROM | Common | 4bpp planar |
| `eeprom1024.ws` | 1024-byte EEPROM | Bandai 2003 extensions | 4bpp planar |
| `eeprom2048-packed.ws` | 2048-byte EEPROM | Bandai 2003 extensions | 4bpp packed |
| `gdma.ws` | None | Common, fast 16-bit ROM | Green screen on success; red on assertion failure |

The five save probes initialize their own stack/segments, increment save word/byte
zero (FF/FFFF means uninitialized), execute IMUL/ADC/ROL, far CALL/RETF and INT/IRET,
check a mapped ROM bank, install line/VBlank/HBlank-timer handlers, read the
keypad after HLT wake-up, and program all four sound channels. SRAM bank 1 on
the 128 KiB image contains the boot count plus 64. EEPROM probes use WEN, READ,
WRITE and controller busy polling; the protocol unit tests additionally exercise
write protection, ERASE, WDS, WRAL/ERAL, abort, separate buffers and all sizes.

On color models, (0,0) is green Screen 1, (9,9) red windowed Screen 2, and (16,16)
a blue high-priority sprite from the VBlank-latched table. The source checks the
model port and uses a monochrome fallback on WonderSwan, so all probes also run
there. Native framebuffer tests separately generate 2bpp color, tile-bank, palette,
flip/scroll, sprite order/window/limit and transparency vectors from memory.

For browser checks, build Wasm/frontend, start Vite preview, then run
`npm run test:compat` from `web` (set `WS_PREVIEW_URL` if needed). The suite selects
these files locally; it does not fetch/upload ROM or save data. To try manually,
choose **Load ROM** and select a generated image; sound defaults to on after
this interaction. Use **Enable audio** if browser policy requires a retry, and
adjust **Volume** or **Mute**.
Reload and reselect the same cartridge to continue its saved boot count; ROMs
are deliberately not cached automatically. Native tests check save bytes; the
browser suite checks the actual localStorage slots and Web Audio buffers.

The separate `gdma.asm` probe uses original constants 1122/3344/5566, byte `OUT`
to program aligned/masked source, destination, length and control registers, and
byte `IN` to assert all eight register values after each copy. CPU instructions
compare all three RAM words after forward and reverse transfers. A successful
Color/Crystal run stores 600D at 0400, 1 at 0402/0404, and draws green; failure
stores 0BAD and draws red. Mono stores 4D4F (skipped) and halts without accessing
GDMA. The native integration test checks these markers, actual RAM and pixels
on all three models. The browser compatibility suite loads this exact ROM through
the existing file picker and checks green output without execution errors on
Color/Crystal. The fixture is freely redistributable under the same CC0 license.

## SDMA and Hyper Voice probes (Issue #19)

`python3 fixtures/build.py` assembles `sound.asm` three times with `SOUND_PATH`
0/1/2. No external waveform files are needed. All three 128 KiB cartridges and
their source/data are CC0-1.0. They initialize stack/segments, detect the console
through A0, and skip color-only sound hardware on mono (marker 0400 = 4D4F,
0402 = 0; silence). On Color/Crystal they draw green and store 0400 = 600D,
0402 = 1 when their register assertions succeed; red/0BAD means failure.

| Cartridge | CPU programming and expected PCM at 24 kHz |
| --- | --- |
| `sound-channel2.ws` | Finite two-byte SDMA, check next source 1002/length 0/last 89=E0, then repeat 32 RAM bytes (sixteen 20, sixteen E0) to Channel 2. Voice volume full both sides. Headphone floats 0.03125 and 0.21875, equal stereo, a 750 Hz square. |
| `sound-hyper.ws` | Same finite/repeat transfers targeting Hyper Voice, signed shift 1, mono-both layout. Finite input latches end E0/E0. Legacy channels off; headphone floats −0.125/+0.125, equal stereo. |
| `sound-direct.ws` | CPU writes to 69 assert alternating +4096/−4096 outputs even in mono-both DMA layout, then checks direct 16-bit outputs. Loops between 16-bit outputs ±8192 and converted 8-bit outputs ±4096, opposite stereo except brief transitions between separate OUT instructions. Headphone floats ±0.25 and ±0.125. No SDMA enabled. |

The two SDMA probes also check high-nibble masks and unused 4D/51 ports, and halt
the CPU while repeat playback continues. These are actual V30MZ instructions,
not host-side port injection. Restart regenerates the same first-frame PCM.
Native `crates/ws-core/tests/sound.rs` checks markers, pixels, exact buffers,
all three models, silence, drain and restart. `npm run test:compat` loads these
same files through the production Wasm player, inspects real Web Audio sample
buffers and verifies gain, mute, pause/resume, visibility, restart and model
selection. The native vectors additionally cover all SDMA and Hyper Voice rates,
bus timing and interactions, signed extension and wrapping mix arithmetic.
See [hardware coverage and limitations](../docs/hardware-subset.md#sound-dma-semantics-and-shared-timing)
and [recorded validation](../docs/issue-19-validation.md).

## Fast sweep probe (Issue #31)

`sweep.asm` builds `generated/sweep.ws`, an original source-included CC0-1.0
128 KiB image with 32 KiB SRAM. On all three models actual CPU byte OUT/IN
checks initial zero control, clearing, FAST_SWEEP readback, fast channel-3
frequency progression, then clearing followed by short-interval stability and
an ordinary frequency step over forty scanlines. The probe freezes sweep before
its fast snapshot so a two-byte read cannot race an update. Its broad fast-delta
bound accommodates approximate CPU timing; exact per-clock timing, signed steps,
nonzero programmable times and transitions are covered by independent unit
vectors. It does not claim to duplicate physical CPU instruction timings.

RAM 0400–040C is copied by CPU instructions to SRAM 0000–000C:

| RAM word | Observation |
| --- | --- |
| 0400 | 600D pass / 0BAD failure |
| 0402 | 1 after clearing OUT/IN succeeds |
| 0404 | Measured fast frequency delta, decimal 32–1536 |
| 0406 | 0100 after a short ordinary interval |
| 0408 | 0101 after the long ordinary interval |
| 040A | Initial control readback 0 |
| 040C | Final control 2, deliberately retained before restart |

Pass draws green on Color/Crystal or gray 170 on Mono; failure draws red or
gray 187. CPU-generated square wavetable bytes then drive channel 1 at 1500 Hz,
equal stereo with headphone samples 0 and 0.2197265625 at 24 kHz. This also
checks that leaving FAST set does not freeze unrelated audio. Native tests and
the complete production-player compatibility suite inspect markers and PCM on
all models, restart from control 2 to initial 0, and verify deterministic buffers
and empty-after-drain in the real Wasm adapter. ROM and save data remain local.
See [source reconciliation](../docs/fast-sweep.md) and
[validation](../docs/issue-31-validation.md). HOLD_CH remains unsupported; these
are emulator regressions, not physical-console or commercial-title results.

## Internal console EEPROM probes (Issue #21)

`internal-eeprom.asm` is original CC0 source assembled into two 128 KiB images:
`internal-eeprom.ws` requests writable settings through header byte 9 bit 7;
`internal-eeprom-protected.ws` requests the normal protected handoff. Both declare
32 KiB cartridge SRAM but never write it, demonstrating independent console data.
The programs run on all three models, starting with six-bit mono commands, then
using ten-bit Color commands on Color/Crystal. They initialize their own segments,
stack, tile data and display. No firmware, title detection or host port injection
is involved. Build/check commands above include both images.

Each reads the owner/settings word at byte 60, increments the shared word at 00,
polls READY and READ DONE, checks separate read/write buffers, WDS/WEN and the
header exception, restores the settings word, sets protection twice through word
OUT BE (including nonzero reserved BF), writes the boundary word at 5E and checks
that writes at 60 fail. Color/Crystal additionally preserve the final physical
word across protected writes and mono/Color transitions. A self-checked pass
stores 600D at RAM 0400 and draws green (Color/Crystal) or gray 170 (Mono);
failure stores 0BAD and draws red or gray 187. RAM 0402 is the shared counter,
0406 the original settings word, and 0408 the last Color word.

The native integration test imports distinct settings/final-word markers, checks
these actual CPU results, settings preservation, independent cartridge saves,
restart, cross-cartridge sharing, export/reimport into a new machine, and all
three model records. Browser compatibility checks load the exact same images in
the production Wasm player and inspect their pass pixels and localStorage bytes.
The browser suite disables the one-second persistence timer in its isolated
console context to prove lifecycle/model flushes themselves retain data; it also
checks reload/reopen, malformed/size-mismatched records, denied console reads and
full console storage with independently working cartridge saves. Injected storage
failures are synthetic. Neither fixture is a physical-console validation result.

## A0 runtime-control probe (Issue #23)

`a0.asm` builds `generated/a0.ws`, an original CC0 128 KiB cartridge with a
fast 16-bit physical header. It copies its control-test body into RAM before
changing ROM width. Actual byte OUT/IN tests zero/all-one/repeated/alternating
writes, ignored reserved/model/status writes and preserved IPL lock on all
three models. Correctly configured aligned/odd ROM reads check the original
31 marker. Width-mismatched ROM data is never read or asserted by the probe.

Color/Crystal additionally copy a matching-width ROM word with GDMA, reject
slow/byte configurations with visible remaining length, and transfer two ROM
bytes through SDMA to Channel 2 and Hyper Voice. Polling detects the first
sample, changes A0 wait while enabled, then checks delivered bytes/counters at
completion (fast to slow for Channel 2, slow to fast for Hyper Voice). These
are emulator regression assertions derived from the documented scope, not
physical hardware certification. The source is independently authored; it does
not incorporate the linked third-party experiments.

RAM 0400 = 600D on pass, 0BAD on failure; 0402/0404 = 1 for the Color/Crystal
GDMA/SDMA assertions (zero on Mono); 0406 = initial A0 (85/87); 0408 = ROM word
3131. RAM 1000 = GDMA word 3131 on Color/Crystal; 1002 remains zero after rejected
copies. Pass pixels are green or Mono gray 170; failures are red or gray 187.
Native `tests/a0.rs` checks markers, bytes, metadata, pixels, restart and model
changes. The production-preview compatibility suite runs the same cartridge
through Wasm/file selection on every model and checks pass pixels after restart.

## Raw 3/6 MiB probes (Issue #25)

`raw-rom.asm` and `build.py` generate `raw3-common.ws`, `raw3-2003.ws`,
`raw6-common.ws` and `raw6-2003.ws`. Their exact lengths are 3,145,728 and
6,291,456 bytes with size codes 05/07; none contains synthetic leading padding.
All four use 32 KiB SRAM, a fast 16-bit header and original CC0 source/data.
Each raw bank n repeats the byte pair `(n XOR 5A), (n XOR A5)`. The final bank
contains the assembled reset program and footer instead, retaining markers after
the code and before the footer. This distinguishes top alignment from raw-length
masking or modulo, including the first bank, interior banks and 64 KiB edges.

The CPU program self-checks first-bank D0/A0 bytes A55A, the bank's final A5,
next-bank A45B, interior bank 16 B54A, leading-gap FFFF and, for 2003, high bits,
D2/D0 aliases and CE self-map reads. Native generated vectors independently cover
all 1024 bank selections, first/last populated bytes, rounded aliases, every C0
window, C2/C3, 2003 aliases and FF fill. No title/hash selects emulator behavior.

On Color/Crystal the program copies four bytes across C2:FFFE → C3:0000 with
GDMA, asserting RAM A55A/A45B and final registers. Slow live A0 then drives SDMA
across that boundary, checking the last sample A4 and source/length/stop state;
slow-ROM GDMA is rejected with its length preserved. Mono skips both engines.
Existing A0/sound/timing probes remain separate and unchanged.

RAM 0400 = 600D (pass) or 0BAD (failure), 0402/0404 = Color GDMA/SDMA pass flags,
0406 = SRAM boot count, 0408 = F000 startup marker, 040A = first ROM word A55A.
Color DMA RAM 1000/1002 = A55A/A45B. Pass pixels are green or Mono gray 170;
failure is red or gray 187. Native integration checks all four images on every
model, restart, compatible model changes, raw lengths and separate console data.
The production Chromium/Wasm suite selects the same local files, checks execution
and restart on every model, exact raw SHA-256 save keys (never padded identities),
renaming, reload/reopen, isolated saves and independent console records. No ROM or
save data is uploaded. Checks verify emulator policy, not physical open-bus
behavior or commercial-game playability.

## Programmable LCD probe (Issue #27)

`lcd.asm` builds `generated/lcd.ws`: original source/data, 128 KiB, 32 KiB
SRAM, CC0-1.0. It executes byte OUT/IN at 16/17 and both immediate and DX word
OUT/IN at 16 on every model. It checks independent STN sync programming (T-3)
and the documented Crystal zero-read policy, polls every raster increment and
wrap for totals 156 and 180, and checks line-144/VBlank plus both timer requests
and timer reload readbacks. These are self-checks executed by the cartridge CPU.

Pass stores 600D in RAM 0400 and SRAM 0000 and draws green (Color/Crystal) or
Mono gray 170. Failure stores 0BAD and draws red or gray 187. RAM 0402/0404
and SRAM 0002/0004 record checked frame line counts 157/181. RAM 0406 and
SRAM 0006 hold the current total (180 initially); Right selects 156 while held,
then returns to 180 on release. RAM 0408 and SRAM 0008 count runtime changes;
SRAM 000A records the checked F0 interrupt flags. Restart reruns all checks.

Native `tests/lcd.rs` checks these markers, framebuffer output, current cadence,
actual frame count, runtime input and restart on all three models. Production
Chromium compatibility checks use the same local file and SRAM markers. An
isolated controlled-RAF context compares the player's actual frame counter to a
second instance of the real production Wasm adapter at explicit timestamps,
including initialization and runtime rate changes, threshold/catch-up vectors,
pause/resume, restart/model selection, visibility and failed-load recovery.
A startup-cached frame duration must fail these assertions. Analog effects and
uncertain edge behavior are policies, not physical-console certification; see
[LCD source reconciliation](../docs/lcd-timing.md).

## Independent keypad and orientation probes (Issue #29)

`keypad.asm` builds `keypad-horizontal.ws` and `keypad-vertical.ws`. Both are
original CC0-1.0 source/data, 128 KiB, with 32 KiB SRAM. Only header orientation
bit 0 and the resulting additive checksum differ. They run the same CPU program
on Mono, Color and Crystal, using monochrome tiles and their own stack/segments.
There are no downloaded assets, firmware, title-specific core paths or host input
substitutes.

The CPU continuously selects all eight B5 combinations (00,10,20,30,40,50,60,70
hex) and stores the complete IN results in RAM 0400–0407 and SRAM 0000–0007.
Tile rows 2–9 show the same byte, least-significant bit first in columns 0–7:
black tile means one; white means zero. The native and production Wasm/browser
tests independently calculate expected values for each of the eleven buttons,
diagonals, mixed rows and release. Browser tests send real keyboard events and
Chromium touch events through the production player's controls.

Asymmetric native markers are a black tile at top left, gray 170 at top right,
gray 85 at bottom left, and a single black pixel at (223,143) on white at bottom
right. Native tests assert the unchanged pixels; browser checks inspect actual
composited screenshots to distinguish counterclockwise portrait rotation from
clockwise or absent rotation. The canvas backing stays 224×144 in both modes.
These are emulator regression probes, not physical-console certification.

## One-line LCD output probe (Issue #37)

`lcd-output.asm` builds `lcd-output.ws`, an original CC0 128 KiB cartridge with
32 KiB SRAM. It uses ordinary line polling, maps, 2bpp planar tiles, a transparent
Screen 2 and a priority sprite. It detects the physical model and uses shade LUT
writes on Mono or RGB12 palette writes on Color/Crystal. No special core path,
firmware, external test asset or copied emulator implementation is used.

At line 40 it changes shades/colors and overwrites tile 0 row 7. Output row 39
must use the new palette but the *old* index 1; a previous-row refetch sees index
3 and fails. Adjacent rows 38/40 and row 47 distinguish translation from tile
composition; the sprite at (16,40) overlaps Screen 2 and remains through row 47.
At line 144 it changes shades/colors again, targeting row 143 after the normal
VBlank/OAM latch. VBlank restores base palettes and tile data for repeated frames.
Native and production browser tests independently assert fifteen literal pixels
and nine complete output rows on all models and after restart. Unit vectors also cover all supported color
layouts, mono on Color/Crystal, overlapping sprites and short/mode transitions.

CPU-written RAM 0400–0408 is mirrored to SRAM 0000–0008: retained boot count,
completed raster passes, observed line after the first writes (40), observed line
after final-row writes (144), and completion marker 600D. Boot increments after
restart; passes must be fresh, preventing stale saved data or old canvas pixels
from satisfying acceptance. ROM/save handling remains browser-local. These are
digital emulator regression policies, not measured sub-line hardware timing.

SHA-256: `0fc51374871dc198415692c7b86abe8947de574632416f4dd470afe0661138fe`.
See [source reconciliation and limits](../docs/lcd-timing.md#one-line-shadecolor-translation-issue-37).

## Relative internal word timing probe (Issue #39)

`word-timing.asm` builds `word-timing.ws`: original CC0-1.0 source/data,
128 KiB, 32 KiB SRAM, fast word-wide ROM header, no firmware or imported assets.
It copies one loop into internal RAM at 2000, then substitutes equal-length
byte/word read/write or IN/OUT instructions between samples. Every sample runs
4096 transfers at identical code addresses. RAM data uses 0800/0801; I/O uses
BC/BD (command word) and BB/BC (valid odd byte lanes). No EEPROM control is
written, no operation starts and no busy wait or external wait is involved.

HBlank one-shot timer observations at A8 measure elapsed line ticks. NEC's
1/1/2 bus-clock rule predicts byte minus aligned = 0, odd minus aligned =
4096 / 256 = 16 ticks. Separate elapsed measurements each quantize endpoints;
all three consumers (cartridge self-check, native test, production browser test)
use the independently derived bounds -2..2 and 14..18 ticks. Bounds are not
fitted to output. The equal-length loops keep instruction addresses, control
flow and stack behavior identical; opcode/prefetch costs common to each group
cancel. No absolute instruction timing or physical pipeline accuracy is claimed.

CPU RAM 0400 is the retained boot count, 0402 is 600D on pass or 0BAD on failure.
0404–0408 contain read byte/even/odd ticks; 040A–040E write ticks; 0410–0414
IN ticks; 0416–041A OUT ticks. These fourteen words mirror to SRAM 0000–001A.
Boot clears the saved completion marker before sampling and increments the
retained count; restart must complete all measurements with fresh CPU markers.
Native tests compare every RAM/SRAM word on Mono/Color/Crystal after twenty
frames and again after restart. The Chromium suite selects the same local file
through the production player/Wasm, verifies each result group and fresh restart,
and checks that no request uploads cartridge/save bytes. The fixture also fails
against the baseline core with its 0BAD self-check marker.

SHA-256: `002bedf305b3fd2c4bde2db74c365d0970b4c8deb5ec8ce5e4c82dec9c64f73c`.
See [transfer evidence and limits](../docs/internal-word-timing.md).

## Multiplication probe (Issue #43)

`multiply.asm` builds the original source-included CC0-1.0 `multiply.ws`,
128 KiB with 32 KiB SRAM, normal footer reset jump, banking and checksum.
SHA-256: `e76afc9641cb24312f3ccddd3c0689d2c097c884729355711ea96166549d52e5`.
No imported ROM, firmware, implementation code or assets are used.

The probe executes unsigned and signed F6/F7, immediate-word 69 and
sign-extended-byte 6B through ordinary decoding. It checks products, complete
FLAGS, actual following ZF/CF/OF conditional-branch decisions, untouched AX/source registers for
immediate forms, source/destination aliasing, stack balance and aligned/odd ES
memory operands. Two incoming flag patterns contrast arithmetic flags and DF.
Every model runs in mono graphics; Color/Crystal additionally run the same
vectors in color graphics and after returning to mono graphics. Unsigned ZF is
selected from physical-model identification, never graphics mode.

RAM 0400–04C6 is copied by CPU instructions to SRAM 0000–00C6. Header words
are completion (600D pass, 0BAD failure), retained boot count, physical model bit
(0 Mono, 2 Color/Crystal), and completed mode passes (1 Mono, 3 Color/Crystal).
Each mode pass contains eight four-word records: destination/product, DX, full
FLAGS and branch bits (bit 0 ZF, bit 1 CF, bit 2 OF). Unused records on Mono
must be zero. The independent native and browser literal expectations are in
`crates/ws-core/tests/multiply.rs` and `web/scripts/multiply.mjs`.

Boot clears all volatile observations, increments the retained count and clears
saved completion before executing any multiplication. Tests deliberately seed
stale pass/garbage SRAM, require every actual observation plus a fresh count,
then repeat after restart. Pass draws green on Color/Crystal or gray 170 on Mono;
failure draws red or gray 187. The browser suite uses the production file chooser,
Wasm player, actual SRAM flush and framebuffer, and checks browser-local data.

See [source reconciliation and limits](../docs/multiplication-flags.md) and
